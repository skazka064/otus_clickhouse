### В чем суть MergeTree
Это движок, который жертвует скоростью точечного поиска и уникальности ради невероятной скорости вставки и аналитических запросов.\
Данные пишутся быстро (кусками), чистятся фоном (слиянием), читаются быстро (разреженный индекс и колонки) и надежно хранятся (репликация).

### Гранула - минимальный неделимый набор данных... первая строка гранулы помечается засечкой
Это сердце архитектуры ClickHouse.
    Гранула: По умолчанию это 8192 строки.\
    Когда вы читаете данные, ClickHouse всегда читает целую гранулу целиком (весь блок).\
    Засечка (Mark): Это указатель на первую строку гранулы. В файле .cmrk2 хранится адрес этой засечки.

### Как это работает с индексами:
В файле primary.cidx хранятся значения первичного ключа **только для этих засечек** (каждые 8192 строк).

```
Пример:
    Засечка 1: значение 2024-07-19 (для строк 1-8192).
    Засечка 2: значение 2024-07-20 (для строк 8193-16384).
```
Если ваш запрос ищет 2024-07-19,\
 ClickHouse найдет Засечку 1,\
прочитает col_dt.cmrk2,\
 узнает смещение,\
 прочитает всю гранулу (строки 1-8192) из .bin,\
 распакует её \
и уже в памяти отфильтрует нужную строку.

### Ключ сортировки должен быть обязательно указан
Если вы не укажете PRIMARY KEY, то первичным ключом автоматически станет ORDER BY

### 1. Физический порядок (ORDER BY) — это "Полный адрес"

Представьте, что ORDER BY — это полный почтовый адрес человека:

    Страна → Город → Улица → Дом → Квартира

Данные на диске физически разложены именно в этом порядке. Это жестко и неизменно.
### 2. Индекс (PRIMARY KEY) — это "Уровень аггрегации"

PRIMARY KEY — это не полный адрес, а только первые несколько полей из этого адреса.
Например, индекс будет хранить только: Страна → Город → Улица.

Почему так? Потому что в индексе хранится значение только для каждой 8192-й строки (гранулы).

Если вы сделаете PRIMARY KEY таким же длинным, как ORDER BY, индекс станет огромным и перестанет помещаться в память, теряя весь смысл разреженного индекса.

### 3. Почему мы не можем сделать индекс ДЛИННЕЕ, чем ORDER BY?

    "Если указан, то должен быть префиксом кортежа ключа сортировки"

Представьте ситуацию:

    ORDER BY = (Город, Улица) (данные отсортированы сначала по Городу, потом по Улице).

    Вы пытаетесь сделать PRIMARY KEY = (Улица, Город) или (Город, Улица, Номер_дома).

Почему первый вариант (Улица, Город) не работает?
Потому что данные на диске НЕ отсортированы по Улице. Если индекс будет ссылаться на порядок по Улице, он будет бесполезен — он не сможет отсекать гранулы, потому что значения Улиц разбросаны по всей таблице.

Почему второй вариант (Город, Улица, Номер_дома) работает, но бессмысленен?
Технически вы можете это сделать, потому что Номер_дома идет в ORDER BY следом за Улицей. Но ClickHouse все равно будет хранить в индексе значение Номер_дома только для каждой 8192-й строки.
### 4. Главный секрет (Зачем мы делаем индекс короче?)

Секрет: Если вы ищете по Городу и Улице, индекс отсечет 99.9% данных. Ему не нужен Номер_дома, чтобы понять, в какой грануле искать, потому что:

    В ClickHouse индекс служит не для поиска конкретной строки, а для ОТСЕЧЕНИЯ целых гранул, которые точно не подходят.
Когда индекс короткий (только Город), он все равно отсечет все гранулы, где нет нужного города. А дальше ClickHouse просто прочитает оставшиеся несколько гранул и уже в памяти отфильтрует их по полному ORDER BY (включая Номер_дома).
### Вывод:
Мы укорачиваем PRIMARY KEY, чтобы:
    Сэкономить оперативную память (индекс меньше).
    Ускорить вставку (меньше данных писать в индекс).
    Оставить дисковой читалке возможность дофильтровать пару лишних гранул в памяти — это дешево.

### Резюме (Запомните эти 3 пункта)
    Порядок (ORDER BY) не может быть короче индекса (PRIMARY KEY). Сначала сортировка, потом из неё выделяем короткий индекс.
    Индекс (PRIMARY KEY) всегда является префиксом сортировки (ORDER BY). Мы не можем индексировать то, что не отсортировано на диске.
    Короткий индекс — это хорошо. Он экономит память и ускоряет всю систему, жертвуя лишь микроскопическим перечтением данных в памяти.

### Итоговая схема жизни куска (Part)
    Рождение (INSERT) → Кусок active = 1 (маленький).
    Созревание (Фоновый Merge) → Кусок А и Б сливаются в В.
    Смерть (После Merge) → Кусок А и Б становятся active = 0, Кусок В становится active = 1.
    Утилизация (Через 8 минут) → Кусок А и Б физически удаляются с диска.

### 1. Базовый MergeTree — фундамент для всех
Это базовый движок, на котором построены все остальные. Он обеспечивает:
    Колоночное хранение, позволяющее читать только нужные столбцы.
    Партиционирование, физически разделяющее данные на папки для эффективного управления.
    Разреженный первичный индекс, который упорядочивает данные на диске и позволяет пропускать большие блоки нерелевантных строк при запросах.
Для продакшена почти всегда используется ReplicatedMergeTree, который добавляет к этим функциям высокую доступность и автоматическую дедупликацию данных при вставке

### 2. SummingMergeTree — для предварительной агрегации
Этот движок предназначен для уменьшения объема данных за счет их суммирования. При слиянии кусков данных все строки с одинаковым ключом сортировки (ORDER BY) заменяются на одну, в которой числовые столбцы просуммированы. Это отличное решение для хранения агрегированных данных, например, для отчетов, где не нужна детализация по каждой транзакции.
Пример: Вместо тысячи строк с продажами для одного и того же товара останется одна строка с общей суммой.

### 3. AggregatingMergeTree — для сложных состояний агрегации
Более мощная версия для агрегации. Он заменяет строки с одинаковым ключом сортировки на одну строку, которая хранит состояния агрегатных функций, например, uniqState или sumState . Этот движок — основа для создания материализованных представлений, позволяя выполнять сложные агрегации инкрементально, по мере поступления данных

### 4. ReplacingMergeTree — для дедупликации и "upsert"
Используется для удаления дублирующихся строк и реализации паттерна "обновления через вставку" (upsert). При слиянии из всех строк с одинаковым ключом сортировки (ORDER BY) остается только одна — с самой последней версией (если указана колонка версии) или просто последняя вставленная . Важно помнить, что это работает асинхронно, и для гарантированного результата при чтении может потребоваться модификатор FINAL

### 5. CollapsingMergeTree & VersionedCollapsingMergeTree — для обработки изменяемых объектов
Созданы для поддержки сценариев, где объекты часто меняются, а обновления в ClickHouse неэффективны. Вместо обновления вы записываете два типа строк: строку состояния (Sign = 1) и строку отмены (Sign = -1), копирующую ключ старого состояния . При слиянии такие пары "схлопываются" (удаляются), оставляя только последнее актуальное состояние . Это позволяет быстро писать поток обновлений, сохраняя лишь конечное состояние.
### VersionedCollapsingMergeTree — улучшенная версия, которая решает проблему порядка вставки. Она добавляет колонку version, позволяя корректно схлопывать строки даже если они поступили в неправильном порядке (из разных потоков) 

### 6. GraphiteMergeTree — для данных мониторинга
Этот движок специально создан для хранения и прореживания данных Graphite. Он позволяет настраивать правила агрегации старых данных для экономии места. Например, данные за последний час можно хранить с точностью до секунды, а за прошлый год — с точностью до часа 

### 7. Replicated*MergeTree — для высокой доступности
Все перечисленные движки имеют свои реплицируемые версии (с префиксом Replicated*). Они используют ZooKeeper или ClickHouse Keeper для синхронизации состояния между узлами кластера, обеспечивая отказоустойчивость .

Ключевое отличие JOIN в ClickHouse (Архитектурная боль)

Прежде чем говорить о типах, нужно понять главное: JOIN в ClickHouse — это всегда боль, потому что ClickHouse — это колоночная OLAP-система, а не OLTP.

    В OLTP (PostgreSQL): Есть B-Tree индексы, статистика, и JOIN оптимизируется планировщиком на лету.

    В ClickHouse: Нет индексов для связей (как в OLTP), данные не уникальны, и самый быстрый JOIN — тот, которого нет.

Именно поэтому в вашем списке есть блок "Рекомендации по оптимизации". Это не просто советы — это инструкция к выживанию.

### JOIN

| Проблема | Решение в ClickHouse |
|----------|----------------------|
| Правая таблица маленькая | Hash JOIN (самый быстрый) |
| Правая таблица большая | Partial Merge JOIN (с записью на диск) |
| Распределенный JOIN | Используйте GLOBAL |
| Нужно "почти точное" совпадение по времени | ASOF JOIN |
| Справочник часто используется | ENGINE = Join + функция joinGet |
| Все тормозит | Денормализуйте данные (добавьте поля из справочника) |

### Агрегатные функции
| Задача | Лучшая функция | Пример | Почему |
|--------|----------------|--------|--------|
| Количество строк | COUNT() | `COUNT(*)` | Самая быстрая |
| Количество уникальных | uniq() | `uniq(user_id)` | Использует хеши (быстрее COUNT(DISTINCT)) |
| Количество уникальных (грубо) | uniqHLL12() | `uniqHLL12(user_id)` | Ещё быстрее, но приблизительно (1-2% погрешность) |
| Сумма | SUM() | `SUM(amount)` | Стандарт |
| Среднее | AVG() | `AVG(price)` | Работает корректно с NULL |
| Список значений | groupArray() | `groupArray(product_name)` | Лучше, чем GROUP_CONCAT в MySQL |
| Топ частых значений | topK() | `topK(5)(category)` | Приблизительно, но очень быстро |
| Первое значение | any() | `any(ip_address)` | Используйте, если уверены в уникальности |
| Макс/мин по условию | argMax() / argMin() | `argMax(price, created_at)` | Находит строку целиком |
